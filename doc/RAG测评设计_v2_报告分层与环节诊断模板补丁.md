# RAG 测评框架 v2：报告分层与环节诊断模板补丁

- 补丁编号：PATCH-REPORT-001；修订：r001。
- 状态：模板及设计建议，待纳入正式契约；尚无报告渲染实现或真实测评结果。
- 依据：[v2 第 9、13、14 节](RAG测评设计_v2.md)、[Reporting C13–C18](../modules/modules/reporting/README.md#contracts)、[诊断报告扩展](../modules/modules/reporting/diagnostic-reporting.md)、[诊断观察规则](../modules/modules/diagnostics/observations.md)。
- 关联切片：[C2 离线评测](../modules/slices/c2-offline-evaluation.md)、[C3 诊断](../modules/slices/c3-diagnostics.md)。

建议把报告设计成“**总体结论 → 环节总览 → 环节问题与证据 → 下一步检查 → 指标及方法明细**”。按环节分组是基础，每组还应统一回答：这个环节负责什么、观察到什么、结果意味着什么、证据覆盖多少、下一步查什么。

现有 Reporting C16 已要求“七阶段按已有系列组织”，因此问题主要在展示约束和阅读顺序尚不具体。本补丁补充可直接使用的模板与映射规则；数值、门禁和诊断仍由已有分析及诊断结果提供。

## 1. 报告先帮助读者做三件事

1. **判断当前结果能否支持决策**：任务成功如何，必选规则是否通过，哪些结论仍未知。
2. **找到应优先检查的环节**：实际观察和证据支持到哪里，中间有多少记录缺口。
3. **进入可复核的实例和明细**：从结论能回查指标、具体用例、实际阶段产物与判断依据。

不要求读者先学习 Faithfulness、EvidenceCoverage 等术语才能读懂首页。指标以“业务问题 + 中文名称 + 技术标识”呈现，例如“回答中的事实有输入依据吗？——事实支持度（Faithfulness）”。

## 2. 三层阅读结构

| 阅读层 | 内容 | 建议展示尺度 |
|---|---|---|
| 总览层 | 结论、门禁、成功/失败/未知、环节检查结果、优先事项 | 首屏或 Markdown 开头，少量关键数字 |
| 诊断层 | 每环节的质量观察、覆盖、证据、竞争解释、代表案例与下一步 | 固定结构，每个环节一个小节 |
| 明细层 | 全指标、精确计数、统计方法、版本、逐题/逐对记录、局限 | 独立附表及 JSON/JSONL，可从上层回查 |

Markdown 首版采用标题、目录、短结论和表格即可。未来交互界面可以把相同语义组织成可展开的环节页；展示层共用同一份报告对象，不能各自计算分数或重新解释门禁。

### 2.1 总览层固定回答四句话

总览文字应从结构化结果按确定规则生成，模板如下：

> **决策状态**：本次发布门禁为〔通过 / 未通过 / 暂不能判断 / 未请求〕，原因是〔具体规则及证据〕。
>
> **总体表现**：〔N〕道预期任务中，已知成功〔S〕、已知失败〔F〕、结果未明〔U〕；可测集成功率为〔S/(S+F)〕，总体成功率的缺失识别范围为〔S/N, (S+U)/N〕。
>
> **主要观察**：〔某环节、某检查范围〕观察到〔具体现象及分子/分母〕；目前证据支持到〔明确边界〕。
>
> **优先下一步**：先〔核验/收集/对照/复核动作〕，用于区分〔竞争解释〕；另有〔缺口〕限制本次结论。

若缺少有效 TaskSuccess，不用 OperationalCompletion 或某一答案维度代填整体成功率。没有合法诊断材料时，“主要观察”只写已有指标结果和缺口，不能生成环节根因。

可测集比例、完整总体缺失范围和统计置信区间分别标注。示例中的公式由 AnalysisResult 提供，渲染器只展示已确认结果。

这里 N 指预先固定且适用该任务成功评价的预期集合，S、F、U 互斥且合计为 N。不适用项及其原因另列；阶段样本、运行次数、主张数和重复尝试数不能混入这个任务分母。

## 3. 环节总览：沿真实能力组织，保留七阶段导航

### 3.1 七阶段导航及内部子环节

| 导航环节 | 人能直接理解的检查问题 | 典型检查项 | 展示边界 |
|---|---|---|---|
| ① 解析与清洗 | 原材料中的关键内容读对了吗？ | 关键字段、表格关系、否定/单位保真、源位置 | 没有固定解析产物时标未接入；不能凭答案错推断 OCR 错 |
| ② 切块 | 证据和条件在分段后还完整吗？ | 必要事实覆盖、跨段条件、结构截断 | chunk 数和长度只描述配置，不代表质量 |
| ③ 表征与索引 | 内容已正确进入索引，并可按所声明条件检索吗？ | 索引范围/更新、独立近邻探针、过滤条件 | 索引清单有文本不等于向量可达；无探针则能力未测 |
| ④ 查询处理 | 系统是否正确理解实体、时间、条件及路线？ | 改写槽位保留、指代、路由、权限范围 | 单凭低召回不能归咎改写；保留实际改写与任务审定 |
| ⑤ 检索、融合、重排与压缩 | 证据找到了吗，排序和压缩后保住了吗？ | 检索候选 → 融合 → 重排 → 压缩的覆盖/充分性及保留 | 内部子环节按已记录实例展开；缺记录时只给较宽边界 |
| ⑥ 组装、生成与引用 | 实际输入充分吗，答案正确完整且有依据吗？ | 最终上下文、任务成功、正确/完整/支持、数值、引用、行动 | 最终上下文归组装子节；输出主张支持归生成子节，分别绑定调用 |
| ⑦ 工程与安全 | 服务稳定、资源可控、权限和策略合规吗？ | 超时/错误、E2E/首字延迟、已知 usage、权限及策略检查 | 系统执行失败与评价器失败分开；未测安全专项不显示安全通过 |

数据集/参考质量、裁判校准和测量完整性作为**贯穿全流程的“评价依据与可测范围”**单独说明，不能因为它们不属于业务链路而藏在附件。

七阶段是报告导航。解析/建库可能离线进行，检索可能循环或并行；导航顺序不证明真实执行顺序。具体病例链路只能来自已核验的 input/output/data_from 等关系。

### 3.2 环节总览表模板

| 环节 | 已有检查结论 | 可测范围与缺口 | 一句话观察 | 去哪里看 |
|---|---|---|---|---|
| 解析与清洗 | 〔未见已测项失败 / 发现失败 / 无法判断〕 | 〔已检查范围；缺哪些记录〕 | 〔观察或未测原因〕 | 〔环节小节〕 |
| 切块 | 同上 | 同上 | 同上 | 同上 |
| 表征与索引 | 同上 | 同上 | 同上 | 同上 |
| 查询处理 | 同上 | 同上 | 同上 | 同上 |
| 检索、融合、重排与压缩 | 同上 | 同上 | 同上 | 同上 |
| 组装、生成与引用 | 同上 | 同上 | 同上 | 同上 |
| 工程与安全 | 同上 | 同上 | 同上 | 同上 |

总览表不同时摆几十个指标。每行显示一项主观察；其余指标在环节内按问题分组。

“已有检查结论”与“可测范围”是两个维度。一环节可以已经发现失败，同时仍有大量未测内容。未知不能抹去已知失败，已有通过也不能抹去缺口。

### 3.3 环节状态的生成规则

建议使用以下展示语义，正式接纳时由版本化 `StageCheckPolicy` 明确检查集和来源：

- **发现已测项失败**：存在绑定该范围的有效失败规则或已成立诊断症状；同时列出未完成检查。
- **已选检查通过**：非空的阶段必选检查清单全部通过，且满足其声明覆盖；必须写清“已选检查”，不能缩成“整个环节健康”。
- **未见已测项失败，仍有缺口**：已有部分有效检查，但不足以作阶段通过结论。
- **无法判断**：缺阶段策略、必要产物、语义审定或有效检查结果。

另列能力状态：`未请求 / 未接入 / 不适用 / 已接入`，不把它们和质量结论混成同一个灯号。报告只使用已登记阈值/规则；不能自行按“>90% 绿、70–90% 黄、<70% 红”猜测健康程度。

可采用文字加颜色增强扫读，但颜色必须有文字标签。环节导航不是新的综合质量分，也不重新计算或覆盖原 GateDecision。

## 4. 每个环节使用同一种小模板

### 4.1 环节小节固定六块内容

```text
〔环节编号与名称〕

这个环节在检查什么：一句业务问题。
结论与范围：已有检查结论 + 可测范围，不扩大成整个环节的保证。

1. 关键观察
   用一句完整的话写现象，带分子、分母及检查条件。

2. 依据
   问题 / 中文指标（技术ID） / 结果 / 方向与标准 / 可测范围 / 明细引用。

3. 影响与解释
   已观测到的任务关联；可支持的解释；尚不能排除的竞争解释。

4. 下一步检查
   具体检查或受控对照，用来解决哪个未知；不承诺未经试验的改进收益。

5. 代表案例
   固定规则选例；问题/实际产物/预期与实际/支持和反证/缺口的受控视图。

6. 其余指标与限制
   辅助指标、未知、异常、测量方法与版本的入口。
```

最小版每环节可以只占一个短段落和一张小表。不要为了排版填满六块而编造证据；无相应结果时显示“未提供/未测”及原因。

### 4.2 指标说明直接放到指标旁边

| 要回答的问题 | 易读名称（技术标识） | 默认需要解释的含义 | 不能据此推断 |
|---|---|---|---|
| 系统完成了请求吗？ | 执行完成率（OperationalCompletion） | 是否得到有来源依据的成功终态 | 请求完成不代表答案正确 |
| 任务真的完成对了吗？ | 任务成功率（TaskSuccess） | 是否满足该题全部必需任务规则 | 不等于某单项质量分或服务可用率 |
| 所需事实找回了多少？ | 已知必要事实覆盖（EvidenceCoverage） | 已审定充分组中覆盖最好的一组的必要事实覆盖 | 不代表全库相关材料已全部召回 |
| 证据足够支撑完整作答吗？ | 已知充分证据组完整率（CompleteEvidenceSet） | 是否完整覆盖至少一套已审定充分路径 | 未命中已知路径不证明没有未知替代路径 |
| 回答符合事实和任务规则吗？ | 答案正确性（AnswerCorrectness） | 检查完整输出，包含额外错误主张 | 只命中某个参考短语不等于全答正确 |
| 必需答点是否遗漏？ | 必需答点完整度（AnswerCompleteness） | 必需答点的满足情况 | 不会单独发现所有额外错误内容 |
| 输出事实有实际输入依据吗？ | 事实支持度（Faithfulness） | 应核验事实主张中受本次实际生成输入支持的比例 | 上下文本身错时，支持度高仍可能答错；也不证明完整 |
| 动作是否合适？ | 预期行动匹配（ExpectedActionMatch） | 正常回答、拒答、澄清等行为是否符合预期 | 动作匹配不等于回答内容正确 |

引用、CER/WER、保留率、ANN recall、阈值判断等其他指标，按实际登记的 metric/profile 提供相同说明。上表不代表所有能力已经实现；没有适用实现或有效审定时就显示能力缺口。

每个指标至少同时展示：结果、分母单位、方向、标准来源、`N_total/N_applicable/N_ok` 或可追溯的等价覆盖、未知/错误原因。query 宏平均和 claim 微平均在名称及单位中区分，不写成同一种“准确率”。

## 5. 两个特别需要的诊断视图

### 5.1 证据在阶段间怎样变化

在检索/重排/压缩/组装环节放一张“证据保留与变化表”：

| 对比的实际阶段 | 共同可测题数 | 两端均完整 | 上游完整→下游不完整 | 上游不完整→下游完整 | 两端均不完整 | 未知/未配对及原因 |
|---|---|---|---|---|---|---|
| 候选 → 重排 | 〔N〕 | 〔n11〕 | 〔n10〕 | 〔n01〕 | 〔n00〕 | 〔完整预期集合中的缺口〕 |
| 重排 → 压缩 | 同上 | 同上 | 同上 | 同上 | 同上 | 同上 |
| 压缩 → 最终上下文 | 同上 | 同上 | 同上 | 同上 | 同上 | 同上 |

检查前提：同题、同 Run、明确阶段实例、相同评价定义和来源范围，两端语义判断有效；若要把差异定位到该传递边界，还需要真实数据关系及旁路核验。

不能只用“候选 80%，最终 65%”说“15% 的题在重排丢了”。两端可测集合可能不同，也可能既有损失又有新增。新表的转移统计需要在 Reporting 分析侧定义新的结果 profile；不能在 Markdown 模板里临时 join/计数。缺少该分析时仅显示原阶段分数与“暂不可作成对保留分析”。

没有中间节点记录时，只能说“候选到最终上下文之间出现变化”，不能自动指向重排。`matched/verified_absent` 只表示锚点定位状态，不能直接充当事实充分性的 1/0。

### 5.2 最终输出同时检查遗漏和新增

生成环节用两列展示质量问题：

| 应保留而遗漏了什么？ | 输出额外说了什么？ |
|---|---|
| 必需答点缺失；限制条件/单位/否定丢失 | 与输入矛盾的主张；输入依据不足的主张；额外错误陈述 |

这样能避免“要点都答到就算成功”，也避免“忠实度高就算整体正确”。

中间阶段的无依据新增也有必要检查，例如压缩器引入新事实，但报告只能展示已有有效 Judgment；现有能力不足时明确标“未评价压缩输出的语义支持”。不能把最终生成忠实度高解释成中间产物没有引入幻觉。

## 6. 现象、解释和行动分开写

| 展示项 | 内容要求 | 示例 |
|---|---|---|
| 已确认观察 | 能由绑定产物、判断或规则直接复核的事实 | 18 个共同可测病例在候选中完整覆盖已知充分组，而最终上下文未完整覆盖 |
| 已观测关联 | 必须有逐题联结和分母；不写成因果 | 这 18 题中有〔实际已分析数量〕任务失败，其余状态另列；未做联结则不显示 |
| 诊断候选 | 仅消费 Diagnostics 的假设与支持/反证/缺口 | 候选至上下文的供给变化，重排、压缩、组装均可能涉及 |
| 下一步检查 | 解决明确的不确定性 | 补中间阶段产物与边关系，再检查是否为截断、压缩或合法过滤 |
| 改进试验 | 有待验证的方案，列明条件和验收 | 在开发集对候选预算/组装策略作受控对照，检查任务成功和资源变化 |

普通 C2 报告没有 Diagnostics 依赖时，可以展示观测和通用的“需补何数据”说明，不输出新的根因候选。C3 报告有合法 Finding/Assessment 时，再补上假设与干预解释。

“建议增大 top-K”“换 embedding”不能作为低覆盖率的自动结论。先区分索引缺失、查询条件错误、候选预算、重排/压缩损失、权限过滤、参考不完整等情况。

优先级来自固定业务规则：门禁阻塞项和高影响违规先列；影响范围、证据强度、未知缺口及人工审查优先级分别展示。没有现成优先级规则时，按固定类别和身份排序，不发明根因概率或“预计恢复 30%”等收益。

## 8. 演示：从数字堆砌改成可读结论

本节为人为构造的模板演示，无真实运行、审定或门禁意义。下述计数假定由有效分析提供；它们只用于检查模板能否讲清楚结论和边界。

### 8.1 总体结论示例

> **门禁未请求**，本报告不提供发布通过结论。
>
> 100 道预期任务中，72 道已知成功、18 道已知失败、10 道结果未明。可测集成功率为 **80%（72/90）**；全量任务的缺失识别范围为 **72%–82%**，该范围不是置信区间。
>
> 在同一批 80 道阶段结果均可测的题中，18 道从“候选完整覆盖已知充分组”变成“最终上下文未完整覆盖”，另有 6 道发生反向变化。现有记录只能定位到候选至最终上下文之间，尚不能区分重排、压缩和组装。
>
> 优先补这一区间的中间产物与传递关系，并复核最终任务失败实例；解析和索引专项未接入，本次不能判断这两部分的质量。

这里 18 道阶段变化不等于 18 道任务失败，两者需要逐题联结才能报告交集。

### 8.2 环节总览示例

| 环节 | 已有检查结论 | 可测范围/缺口 | 主要观察 |
|---|---|---|---|
| 解析与清洗 | 无法判断 | 未提供固定解析输出 | 未评价原文到解析产物的保真 |
| 切块 | 无法判断 | 未提供完整切块范围 | 不能检查证据是否在切块时丢失 |
| 表征与索引 | 无法判断 | 未接入独立索引/近邻探针 | 检索结果不足以认证索引正确 |
| 查询处理 | 无法判断 | 未提供实际改写和路由记录 | 不能判断是否改错年份或实体 |
| 检索、融合、重排与压缩 | 已观察到阶段差异；任务影响待核验 | 两端共同可测80/100；中间产物缺失 | 18题由完整变不完整，6题反向变化；不归咎具体子环节 |
| 组装、生成与引用 | 发现任务失败，其他检查有缺口 | TaskSuccess有效90/100；引用专项未接入 | 18题已知失败、10题未明；错误类别须看已提供维度判断 |
| 工程与安全 | 发现运行失败；安全无法判断 | 运行终态100/100；安全专项未测 | 96次完成、4次超时；不能由“无安全日志”推断安全 |

演示假定 4 次超时经合法任务规则判为 fail，并已包含在 18 道任务失败中。运行完成 96% 不替代任务成功的两种分母口径。

### 8.3 检索至上下文的环节小节示例

**检查问题**：检索候选中已有的已知充分证据，在实际最终上下文里还完整吗？

**结论与范围**：观察到双向变化；两端有共同可测记录 80 题，其余 20 题缺有效阶段判断。中间环节未记录，暂不能指出具体发生点。

| 指标/检查 | 结果 | 如何理解 | 标准/判断 |
|---|---|---|---|
| 候选的已知充分证据组完整率 | 80%（64/80） | 64题候选完整覆盖至少一组已审定路径 | 未配置阶段通过标准，不显示环节通过 |
| 最终上下文的同口径完整率 | 65%（52/80） | 52题实际上下文完整覆盖已知路径 | 同上；不等于真实可答率 |
| 两端完整率差 | −15个百分点 | 共同集合上的净变化为−12题 | 不能解释成“丢失了12题” |
| 完整→不完整 | 18题 | 两端充分组判断发生该转移 | 不是已证明的任务错误原因 |
| 不完整→完整 | 6题 | 两端发生反向转移 | 检查是否来自新增材料、重组或合法替代支持 |

对应的完整转移表：

| 候选状态 | 最终上下文完整 | 最终上下文不完整 | 小计 |
|---|---|---|---|
| 完整 | 46 | 18 | 64 |
| 不完整 | 6 | 10 | 16 |
| 小计 | 52 | 28 | 80 |

**解释与下一步**：先补重排、压缩和组装的实际产物及边关系，再核查该18题的证据变化和任务结果。反向变化可能来自其他材料或组装路径；没有完整数据关系时不能把这80题画成只允许损失的单向漏斗。若已知路径丢失但存在有效替代路径，应更新相关事实判断及参考版本，不能直接断言上下文不足。

**案例入口**：按固定 ExamplePolicy 选取对应样例；正文展示允许的元数据及已有 DisplayView。没有受控视图时不嵌入原问题、源文或参考答案。

### 8.4 任务与支持度不一致时怎样解释

| 观察组合 | 应写的说明 | 不能自动下的结论 |
|---|---|---|
| 完整度高，正确性失败 | 必需答点可能已覆盖，但完整输出仍有错误；查看额外主张、数值与条件 | “模型已经答对，只是分数低” |
| 支持度高，正确性失败 | 回答可能忠实于有误输入，也可能存在不同维度错误；需审查来源与任务 | “没有幻觉，所以答案正确” |
| 已知充分组完整，任务仍失败 | 在所审定证据条件下仍未完成任务，形成生成/任务理解/参考等候选解释 | “已证明唯一问题是生成模型” |
| 任务成功，但中间记录缺失 | 本次任务通过；中间阶段仍未评价 | “整条链路全部正常” |
| 支持度未知 | 主张清单、实际输入或支持标签不足，需补测量 | “0分幻觉”或“默认无幻觉” |

## 9. 报告对象与展示规则怎样落地

### 9.1 新增展示配置，不把推理写在模板里

建议增加版本化 `ReportLayoutPolicy`，作为正式接纳后的展示 profile 扩展，描述：

- 七阶段及子节的顺序、中文标题、阅读问题。
- 具体 `metric_id/version/profile/instance_id + target_semantics/scope` 到环节的映射。
- 代表指标、辅助指标、指标释义及明细引用位置。
- 总览事实的白名单句式、必要输入、缺口回退语句。
- 阶段检查清单/规则的引用、已有诊断结果的引用和展示约束。
- 版本、示例策略与与 C2/C3 的适用范围。

不能只按指标名分组：同名 EvidenceCoverage 在 candidate、rerank、final_context 属于不同实际范围。一个指标可以在首页和详情复用同一结果引用，不能因此在统计中重复计数。

拟议的 `StageSection` 只负责组织已有事实：

```text
stage_id / title / reader_question
scope_refs / capability_status / stage_check_result_ref
headline_fact_refs / metric_result_refs
diagnostic_finding_refs（可空）
measurement_gap_refs / followup_action_refs
example_manifest_ref / limitations
```

这是新设计建议，不是当前严格 DTO 已允许的任意字段扩展。正式采纳时需要 schema、引用绑定、规则版本、测试与兼容迁移。

### 9.2 三类内容由谁生成

| 内容 | 所有者/来源 | Renderer 的职责 |
|---|---|---|
| 计数、宏平均、区间、成对差及缺失范围 | Reporting 分析结果 | 仅格式化、单位和舍入展示 |
| Gate及其阻塞原因 | GateDecision | 原样保留结论，不能靠颜色/总分改写 |
| 阶段失败事实、跨阶段关联统计 | 已确认评价/规则及新增分析 profile | 核验绑定，显示适用范围 |
| 假设、竞争解释、支持反证和建议检查 | Diagnostics Finding | 组织和引用，不创造新根因 |
| 干预资格、效果及范围 | Diagnostics Assessment | 显示严格/非严格/未核验、四转移和完整分母 |
| 指标的中文问题与固定释义 | 版本化指标说明/布局策略 | 与精确 metric/profile 匹配 |

首版不需要调用语言模型来总结。确定性模板能够先保证结论与数据一致。未来若加语言模型润色，其文本须逐句绑定已有事实、保留限定词并校验数字，不能成为数值或诊断事实的权威来源。

### 9.3 分阶段接纳

1. **C2可先完成**：调整展示顺序，加入中文问题和指标释义，按真实 scope 分组，提供环节可测矩阵、覆盖、异常及固定案例入口；没有新增分析时保留“不支持阶段转移统计”。
2. **正式扩展后完成**：阶段检查集、共同病例转移表、任务关联计数，以及新的阶段级可复核分析结果。它们需要明确分母、unknown处理和结果 profile，不能只改 Markdown。
3. **C3数据具备时启用**：诊断候选、证据链、竞争解释和Oracle结果。保持普通基线、干预结果和发布门禁各自范围，不因为Oracle恢复就改原门禁。

已有 `report.md/report.json` 与诊断报告的包结构、当前访问检查、固定选例和受控导出规则继续使用。本文提出的是新展示版本，不自动覆盖现有 Confirmed profile。

## 10. 模板验收清单

以下为待实施时的验收案例，不代表已有实现测试已执行。

| 输入或场景 | 预期呈现 |
|---|---|
| 解析/索引数据未接入 | 总览明确无法判断，不显示绿色“正常” |
| 任务成功且中间阶段未测 | 任务通过与阶段缺口同时可见 |
| 同环节有一项已知失败、另几项未知 | 已知失败保留，未知另列，不相互抵消 |
| 缺阶段阈值或必选清单 | 展示数值和观察，不推导阶段通过 |
| 100题72成功18失败10未知 | 可测80%；全量识别范围72%–82%，两者明确分开 |
| 服务96次完成、4次超时 | 服务完成率96%；不替代整体任务成功 |
| 两端分数下降但可测集不同 | 不输出保留率或同题损失数量 |
| 64/80变为52/80，损失18、获得6 | 净差−15个百分点；损失与获得分开显示 |
| 缺重排/压缩中间节点 | 只报告候选至上下文较宽边界 |
| 只有锚点matched/absent | 不自动改成语义覆盖/充分判断 |
| Faithfulness高、Correctness失败 | 解释检查问题不同，不自动判矛盾或整体通过 |
| 主张和数值指标使用不同分母 | 单位、宏/微口径与覆盖明确，禁止混成总分 |
| Oracle fail→pass | 限定为该选择条件下恢复，不写成检索根因占比 |
| A/B结果共用不同样本集 | 展示双方覆盖、共同集及排除原因，不直接比较独立均值 |
| 难度/题型标签缺失或未正式发布 | 归missing_value/未支持，不从答案猜标签 |
| 没有合法DisplayView | 保留元数据和缺口，不补原文或参考答案 |
| 代表案例配额只展示少数失败 | 明示候选数、所选数和未展示数；完整失败仍参与分析/门禁 |
| Markdown与JSON | 引用同一事实、分母、状态与Gate；显示舍入不改变结论 |

验收目标是读者无需翻指标字典，就能从首页说清：结果如何、哪些环节已有问题证据、哪些环节尚未测清、下一步应该验证什么。完整指标仍可追溯，但它们承担的是结论依据。
